# VS-001: Project skeleton
Status: DONE

## Goal
Runnable FastAPI project with Docker Compose (api, worker, postgres, redis) and a health endpoint.

## Scope
- pyproject (deps, ruff, pytest config), app factory, config via pydantic-settings, `.env.example`
- `GET /health` -> 200 `{"status":"ok"}`, plus `GET /health/ready` checking DB + Redis
- Dockerfile, docker-compose.yml, empty arq worker that starts
- One test for /health

## Out of scope
DB models, webhooks, OpenAI.

## Acceptance
- `docker compose up --build` starts all 4 services
- /health returns 200, /health/ready reports DB and Redis OK
- pytest passes

## Understand first
Containers vs images, why api and worker are separate processes, env vars for config.

## Notes
- Dependency manager is uv (`pyproject.toml` + committed `uv.lock`). The Docker image
  installs with `uv sync --frozen` and puts `/srv/.venv/bin` on PATH, so `pytest`,
  `uvicorn`, `arq` and later `alembic` run as bare commands inside the container.
- `Settings` uses `extra="ignore"`. pydantic-settings defaults to `extra="forbid"`,
  which would reject `.env` outright because `.env.example` already lists the Meta,
  OpenAI and Booking keys that later slices need.
- `/health` does no I/O, so it stays 200 during a dependency outage. `/health/ready`
  probes both dependencies through FastAPI dependencies and returns 503 when either
  fails, naming the failing one in the body. Probe failures log the dependency name
  only — connection errors embed the DSN password (hard rule 9).
- Each probe runs under `asyncio.timeout(2)`. A dependency that accepts the connection
  and then goes silent is the case a plain `except` never catches; without the bound,
  `/health/ready` would hang instead of answering. Timeouts log a distinct message from
  refusals, because the two need different fixes.
- Step 11's live run logged `readiness probe timed out for dependency=redis`, not
  `failed`. Stopping a container makes the DNS lookup for its name slow rather than
  instantly failing, so the 2s bound fires first. In practice "timed out" means "no
  answer within PROBE_TIMEOUT_SECONDS for any reason, including slow name resolution",
  not specifically "accepted the connection then went silent".
- The Dockerfile pins uv with a hardcoded tag, `ghcr.io/astral-sh/uv:0.12.19`, matching
  the uv installed locally. The tag carries a comment to keep the two in sync, and
  `docker compose exec api uv --version` checks it.
- All three published ports bind `127.0.0.1` only. Postgres and Redis run with well-known
  dev credentials (Redis with none at all), so `0.0.0.0` would hand the local network a
  database. The api is loopback too: tunnels (ngrok, cloudflared) run on the host and
  reach it through localhost, and WhatsApp webhooks arrive through the tunnel.
- The first `up` hit a host port collision with another local compose project. It left
  the redis container created but with no network attachment; a retry did not recreate
  it because its config was unchanged, and its healthcheck (redis-cli inside the
  container) still reported healthy. `docker compose down` then `up` fixed it. A
  container healthcheck proves the process is alive, not that it is reachable.
- `DATABASE_URL` and `REDIS_URL` are required with no defaults, so a missing config
  stops the process instead of starting a half-working API.
- The worker registers one trivial `ping` job. arq refuses to start a worker with no
  functions and no cron jobs, so a literally empty worker was not possible.
- `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` were added to `.env.example`.
  They configure the local Postgres container only; the app reads `DATABASE_URL`.
- Postgres applies `POSTGRES_PASSWORD` only when it first initialises the
  `postgres_data` volume. Changing it later needs a matching `DATABASE_URL` and
  `docker compose down -v` (which deletes local data).

## Follow-ups
- Container healthchecks for `api` and `worker` (VS-001 only added them for postgres
  and redis).
- A multi-stage Dockerfile and a non-root user before anything goes to production;
  the current image is a single stage, runs as root and ships the dev dependency group.
- Structured JSON logging with a request id, once there is a request worth tracing.
- Readiness worst case is about 2x `PROBE_TIMEOUT_SECONDS`: FastAPI resolves the two
  probe dependencies sequentially. The api container healthcheck timeout must exceed
  that, or the probes should run concurrently.
- VS-003's tunnel will expose the whole api, including `/docs`, `/openapi.json` and
  `/health/ready`. Restrict the tunnel to the webhook path or disable the docs outside
  development.
- No service has a restart policy; the worker exits permanently once arq's Redis
  retries run out. Add `restart: unless-stopped` for api and worker, alongside the
  container-healthcheck follow-up.
- A probe cancelled by `asyncio.timeout` leaves an orphaned future that asyncio logs as
  `ERROR asyncio Future exception was never retrieved` with the raw exception repr.
  Seen live with a `socket.gaierror` (hostname only). This is the known exception to the
  "dependency name only" note above: that guarantee covers what our own handlers log, and
  this line comes from asyncio itself, outside them. Handle it so timeouts log only our
  own message, and verify the behaviour against a stopped Postgres.
- The no-credential log test covers only the database probe; add the Redis equivalent.
- `docker-compose.yml`'s `${POSTGRES_*:-doctoleb}` defaults are credential literals. Fine
  for local dev; before any non-local use, require them with `${VAR:?}` and drop defaults.
