# VS-007: Booking tools
Status: PARTIAL

### Two messages for every change (the confirmation gate, V3)

A change is **prepared** while answering one patient message and can only be
**executed** while answering a later one. `booking_actions.state_for` computes the
verdict in SQL as one boolean, `confirmable`, so a tool checks a flag and cannot
half-apply the rule. Four conditions:

1. the prepared row is still `PENDING`;
2. the message being answered is not the one that prepared it;
3. some reply of ours was **actually sent** (`sent_at` set) after the row was written
   and before this message was stored;
4. for holds, the expiry has not passed on the injected clock (T1's `expire_pending`
   has already turned such rows into `EXPIRED`).

Condition 3 is the one that does the real work. It is stronger than "an earlier
message": two quick messages do not count as a confirmation, and neither does a
message answering a reply a takeover dropped or Meta refused. `sent_at` is set by
`attach_provider_id` and `mark_sent_without_id` and by nothing else, so a failed
reply can never satisfy it.

The residual gap: a patient who types "yes" to something else just after our question
arrives. The prompt's "clearly confirms" and the ⏳ line carry that part.

`cancel_appointment` is a **two-call** tool, because there is no hold to prepare a
cancellation with: the first call prepares and cancels nothing, and a second call with
the same `appointment_id` executes it.

### `booking_actions`: what is kept between messages (V2)

Ids, codes and one operational expiry. Never a name, an appointment or slot time, a
doctor, a tool result, the patient reference or an argument value - two tests pin the
exact column set and that no column is unbounded `TEXT` except `tenant_id`. A partial
unique index allows at most one `PENDING` row per conversation, which is what makes
"the prepared change" a single thing even when two quick messages produce two turns.

`hold_id` lives here and **never reaches the model**: the tools that consume a hold
read it from this table, so the model can neither invent nor reuse one.

### Idempotency keys (V1, hard rule 6)

`sha256_hex("doctoleb/booking-idempotency/v1" \n webhook_inbox row UUID \n tool name \n
canonical JSON of the body)`. Sorted keys, no whitespace, every value NFC-normalised.

Never a wamid: a wamid decodes to the patient's phone number and the key reaches the
Booking Service's logs. `idempotency_key` takes a `uuid.UUID`, so passing one is a
`TypeError` rather than a silent leak. Our inbox row is 1:1 with the source message
(hard rule 2's dedupe), so hard rule 6 holds in substance.

The key is identical across retries because every input is: the prefix, the row, the
tool, and a body whose only model-supplied parts (`slot_id`, `full_name`) are validated
and normalised first. A re-run that spells the name differently gets a different key,
and V13's natural idempotency at the service covers that instead.

### The in-memory Booking Service (V8) and its lifetime

`FakeBookingClient` stays frozen, stateless and read-only; `InMemoryBookingService`
wraps it for the catalogue and holds the write state. One instance per worker process,
built inside `startup()` so its `asyncio.Lock` belongs to arq's loop, and shared by
every job the process runs at once.

- **everything is lost on a restart** - holds, appointments and the replay store.
  `booking_actions` rows then point at holds the service does not know, and
  `book_appointment` answers `NOT_FOUND`, which the tool reports as "the hold ran out";
- **several worker processes would each have their own state**, so one patient could
  see different availability from one message to the next. **Run exactly one worker**;
- slot ids are opaque tokens (`slot_` + a keyed hash), unguessable, per tenant, and
  resolvable only by the instance that issued them.

### The reply guard (V4) and what it cannot do

G1: our code appends a receipt line built **only** from the service's answer - ⏳ held
or prepared, ✅ booked, 🔁 moved, ❌ cancelled, with the reference only for a change that
happened. A `PENDING_APPROVAL` booking gets ⏳, never ✅.

G2: the model's own words are scanned, **before** the receipt is appended, for booking,
cancellation and change claims in Arabic, Arabizi, French and English. A claim the
turn's own outcome does not allow replaces the reply with `AGENT_FALLBACK_REPLY` and
writes an `agent_unconfirmed_claim` dead letter. The check is per kind, so a
"cancelled" claim after a booking is still caught.

Known limits, each pinned by a test so they are documented rather than discovered:

- **a false positive:** "Would you like it booked?" is flagged, and the patient gets
  the fallback. That is the safe side;
- **false negatives:** "Your booking is done." and "5alas, mnshoufak l arb3a" pass. The
  missing ✅ is then the only tell;
- the lexicon cannot be complete, negation handling is a three-word window, and the ✅
  line only helps once patients learn that it is the proof.

### Unknown outcomes (V6)

A timeout or a lost connection is `UNAVAILABLE` on a **read** and `UNKNOWN_OUTCOME` on
a **write**, because a write may have been applied before its answer was lost. The
patient is told neither that it worked nor that it failed; `tool_executions.status`
and `booking_actions.status` are `UNCERTAIN`; and a `booking_uncertain` dead letter
carries the idempotency key so a human can find the request. An uncertain **hold** is
recorded and not dead-lettered: it expires by itself.

### What is recorded, and what never is

| | The model sees | Stored by us | Never, anywhere |
|---|---|---|---|
| Tenant | never | every row (`TEXT`) | a schema, argument, result, message to the model |
| Patient reference (the phone number) | never | only as `contact_identities.external_id`, where it already was | a schema, a result, a log line, `booking_actions`, a dead letter |
| Patient's name (`full_name`) | its own tool-call arguments | only inside `messages.text`, where the patient typed it | a log line, `tool_executions` (names only), `agent_runs`, `booking_actions`, a dead letter, the stand-in's memory |
| `slot_id`, `appointment_id` | yes | `appointment_id` in `booking_actions` | a log line |
| `hold_id` | never | `booking_actions` | a result, a log line |
| Idempotency key | never | `booking_actions.last_idempotency_key`, booking dead letters | a log line, a result |
| Doctor names and times | yes (results) | only inside `messages.text` (the reply and its receipt) | a log line, the agent tables, `booking_actions`, a dead letter |
| Reference code | never | only inside the receipt, in `messages.text` | a log line, a result |

### V14 was overridden by the developer

The plan's default was our contact row UUID as the patient reference. The Booking
Service owner asked for the patient's **WhatsApp phone number** instead, so that is
what is sent: exactly as stored, with no normalisation and no added `+`. **The exact
format is still to be confirmed** by the Booking Service owner. Because it is personal
data it travels in a header, never in a URL or query string, and it is `repr=False` on
`Turn`. `docs/booking-contract.md` records the change under "Proposal: the write side".
