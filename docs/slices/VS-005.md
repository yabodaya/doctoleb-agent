# VS-005: AI replies
Status: PARTIAL
Code complete on `feat/vs-005-ai-replies`. The live test with a real phone
(Task 9 of `docs/plans/VS-005-plan.md`) has not run, and it cannot until

## Goal
Replace the fixed reply with an OpenAI-generated reply using conversation history.

## Scope
- `app/integrations/openai/` wrapper (model from env, timeout, retries)
- `agent/process_turn()` (no tools yet): system prompt + last N messages -> reply
- System prompt in a versioned file: role (clinic receptionist), language (reply in the patient's
  language: Arabic, English, French, Lebanese Arabizi), admin-only boundary
- Re-check conversation state before sending (hard rule 7)

## Acceptance
- Natural conversation on WhatsApp in Arabic and English
- Test: if conversation flips to HUMAN_ACTIVE during processing, no AI message is sent
- Tests mock OpenAI; no real API calls in CI

## Understand first
Chat message roles, context window, why history is trimmed.

## Notes

### The four commit boundaries, and why generation runs outside all of them
```
T0  claim the inbox row                                              COMMIT
T1  tenant, contact, conversation, the inbound message
    hard rule 7, FIRST read; load the history
    ------------------------------------------------- COMMIT, session CLOSED
    generate: one attempt, a wall-clock deadline, NO transaction open
T1b hard rule 7, SECOND read; reserve the reply WITH its text
    (a generation failure's dead letter is written HERE)             COMMIT
    send the row's STORED text to Meta - one attempt, a deadline
T2  wamid, SENT, sent_at; inbox row PROCESSED, lease cleared         COMMIT
```
`MessageRepository.add` updates `conversations.last_inbound_at` for an inbound
message, and that `UPDATE` row-locks the conversation until the transaction
ends. A staff member taking the conversation over is an `UPDATE` of the same
row, so it would wait — for the whole model call, up to
`OPENAI_TIMEOUT_SECONDS`. Generation therefore runs *outside* the
`async with sessionmaker()` block, not merely after its `commit()`: outside the
block, no stray query can autobegin a transaction that then stays open across
the call. Both takeover tests arm `SET LOCAL lock_timeout = '2s'` in the staff
session, so a regression fails in two seconds and names itself instead of
hanging the suite.

### Generate, then reserve WITH the text, then send the STORED text
VS-004 made the reply row the durable "a reply is in flight" marker. VS-005
makes it the **decision** too: once a text is reserved, that text is the reply.
Reserved empty and filled in afterwards, a crash between the model call and the
write would make the retry ask the model again — a second bill, and possibly a
different answer. Generating first and reserving *with* the text closes that: a
retry that finds a reserved row sends exactly what is in it and never calls the
model.

VS-004's duplicate-reply gap (a crash after Meta accepted and before the wamid
is saved) is unchanged — but the duplicate it can produce is now the *same*
text twice, never two different answers.

### Hard rule 7 is read twice, and only the second one is the guarantee
Both reads use `ConversationRepository.current_state`, which selects the state
**column**. A `select()` for the mapped entity in a session that has already
loaded the conversation is answered from SQLAlchemy's identity map, so a
"re-read" through `get` would never see a commit made by anyone else — which is
the only thing it exists to see. A test makes `get` raise for the whole message
path.

- The **first** read, in T1, is an optimisation and a privacy measure: a
  conversation a human already holds costs no model call, and none of the
  patient's words are sent to OpenAI for nothing.
- The **second** read, in T1b after the model and immediately before the
  reservation and the send, is hard rule 7's guarantee. The model call is the
  longest thing the job does, so the check that protects the send has to come
  after it.

### One retry layer
The OpenAI SDK retries internally by default — `max_retries=2`, so three
attempts per call (verified against openai 3.20.0). Inside five job tries that
is fifteen requests, fifteen bills, and a dead letter reporting five attempts.
`max_retries=0` is set on the client and asserted by a test.

Classification happens in exactly two functions in
`app/integrations/openai/chat.py`, and nothing outside that module ever sees an
SDK exception or a status code:

| What happened | Outcome | Reason code |
|---|---|---|
| `OPENAI_API_KEY` blank | PERMANENT, no request | `openai_api_key_unset` |
| `OPENAI_CHAT_MODEL` blank | PERMANENT, no request | `openai_model_unset` |
| our wall-clock deadline, or `APITimeoutError` | RETRYABLE | `openai_timeout` |
| `APIConnectionError` | RETRYABLE | `openai_connection` |
| 429 with `code` or `type` `insufficient_quota` | **PERMANENT** | `openai_insufficient_quota` |
| any other 429 | RETRYABLE | `openai_http_429` |
| ≥500, and 408 | RETRYABLE | `openai_http_<status>` |
| any other 4xx | PERMANENT | `openai_http_<status>` (+ `_<code>` when code-shaped) |
| another `APIError`, or a 2xx that is not a completion | RETRYABLE | `openai_bad_response` |
| `finish_reason` `length` / `content_filter` / anything but `stop` | PERMANENT | `openai_reply_truncated` / `openai_content_filter` / `openai_unexpected_finish` |
| `stop` with empty or whitespace content | PERMANENT | `openai_empty_reply` |
| any exception that is not an OpenAI error | **raises** | a bug in our code, not an outage |

**408 is retryable** — read as a timeout, which is what the SDK's own retry set
does. **409 stays permanent** as "another 4xx", although the SDK would retry
it. **`insufficient_quota` is permanent although it is a 429**: retrying cannot
buy credit, and five tries would only delay the fallback by the whole
75-second backoff curve.

A truncated reply is never sent: half a sentence from a clinic is worse than
the fallback, and the dead letter names the fix
(`OPENAI_MAX_OUTPUT_TOKENS`, or a non-reasoning model).

### Why both timeouts are wall-clock deadlines
An httpx (and httpx2) float timeout applies **per connection phase** —
`Timeout(30.0)` is `connect=30, read=30, write=30, pool=30` — so one call can
legitimately take several times its value. `JOB_TIMEOUT_SECONDS` is supposed to
cover `OPENAI_TIMEOUT_SECONDS + META_SEND_TIMEOUT_SECONDS`, and an arq job that
exceeds its timeout is finished as **failed and never retried**: none of our
`except` blocks run, so there is no dead letter, no lease release, and nothing
re-enqueues the event. Both calls are therefore wrapped in `asyncio.timeout`,
and `MetaClient` got the same treatment as the OpenAI client (VS-004 follow-up,
closed here). `classify_exception` learned the built-in `TimeoutError`, or our
own deadline would escape as though it were a bug in our code; its reason code
is `http_timeout`.

A cancelled call may still be billed by OpenAI if the server finished it.
Bounded by `JOB_MAX_TRIES`.

### The fallback
When generation fails permanently, or retryably on the last try, the patient
gets `AGENT_FALLBACK_REPLY` through the **same exactly-once path** as any
reply: reserved with its text, committed, sent, wamid saved. The outcome is
`replied_fallback` and the inbox row is `PROCESSED`, **not** `FAILED` — the
patient *was* answered, and `FAILED` would also make the event claimable again
by `claim()`.

A dead letter still records the generation failure, and it is written **in the
same transaction as the fallback's reservation**. Written earlier, in its own
transaction, a crash before the reservation would leave a dead letter for a
failure that had since healed; written later, with the wamid, a crash during
the send would lose it. In T1b the two facts commit together or not at all, and
a retry that finds the reserved fallback sends it and writes nothing further.

A fallback then refused by Meta leaves **two** dead letters, `openai_*` and
`http_*`. That is accurate: two different things went wrong, each with a
different fix.

### A reserved reply that will never be sent is marked FAILED
Two paths used to leave a reply row `QUEUED` forever: hard rule 7 dropping a
reply an earlier try had reserved, and a Meta send failing retryably on the
last try. Requirement 5 skips *failed* outbound messages from the history, but
a `QUEUED` row nobody will ever send would reach later prompts as something the
clinic said — while still claiming a reply was on its way. Both paths now mark
it `FAILED`, which is also hard rule 5's shape.

### What the model sees, and what it never sees
One request per reply: the system prompt, then up to `AGENT_HISTORY_MESSAGES`
earlier messages of **this conversation** oldest first, then the message being
answered as the last `user` message.

- `INBOUND` → `user`, `OUTBOUND` → `assistant`.
- Earlier messages are those created **before** the one being answered, tenant-
  scoped, this conversation only, with **failed outbound skipped in SQL** so
  that N counts only what the model will see. The cut matters: two messages a
  second apart produce two jobs, and the job answering the first can find the
  second already stored.
- The `created_at` anchor is read **in SQL** through the answered message's id,
  never from the ORM attribute: after an INSERT a server-default `created_at`
  may not be loaded, and loading it under `AsyncSession` raises
  `MissingGreenlet`.
- A message with no text becomes a **fixed** placeholder —
  `[patient sent a voice note]`, or
  `[patient sent a photo, file, location or other non-text message]`. Never
  derived from the payload: a media id or a caption is still patient content.
  One generic placeholder for every non-text type, because `messages` stores no
  Meta type.
- **Never sent:** the WhatsApp profile name, the phone number, any wamid, and
  no tenant, contact, conversation or inbox id. `tenant_id` is carried on the
  `Turn` for VS-006's tools and is not read by `build_messages`. An end-to-end
  test greps the real request body for all of them.
- `store=False` on every request, so patient content is not kept by OpenAI for
  its distillation or evals products.

### The prompt
`app/agent/prompts.py` holds `SYSTEM_PROMPT` and `SYSTEM_PROMPT_VERSION`
(`vs005-1`). A test pins the text's SHA-256 to the version, so the text cannot
change without the version changing, and the job logs the version with every
generation — a change in the AI's behaviour can be matched to a change in its
instructions. Each rule has its own test: no schedules, prices, doctors or
bookings; never says anything is booked; the clinic team will follow up; no
medical advice; the emergency notice first for urgent messages; four languages;
short WhatsApp style; patient text is data, not instructions; and — one
addition beyond the requirements — **never claim to be human**. That last one
is a baseline of honesty, not the AI-disclosure question (follow-up 3), which
is the clinic owner's call.

The emergency sentence names no number on purpose: see follow-up 5.

### `.env.example` did not boot before this slice
`.env.example` lists every key with an empty value, and `docker compose`'s
`env_file:` turns `KEY=` into an empty environment variable. pydantic rejects
`""` for a float or an int, so `Settings(_env_file=".env.example")` raised
**six validation errors** — on VS-004's own numeric keys, before VS-005 added
any. A `.env` copied from the example file started neither the api nor the
worker, and that is the file VS-004's live test tells you to copy.
`env_ignore_empty=True` makes a blank value mean "unset"; a blank *credential*
still means "not configured", because its default is already `""`, and a blank
*required* value (`DATABASE_URL`) is still a loud failure at boot.

### The SDK runs on httpx2, and no test can reach OpenAI
`openai` 3.20 depends on **httpx2**, a separate package from the `httpx` the
Meta client uses. So: the test transport is `httpx2.MockTransport`; the
transport loggers to silence are `httpx2` and `httpcore2`; and the SDK keeps
its own connection pool, closed separately on worker shutdown.

`configure_logging` pins `openai`, `httpx2`, `httpcore2` and `httpcore` at
`WARNING` or above and `httpx` at `INFO` or above, as a **floor** — `max()`, so
`LOG_LEVEL=ERROR` still wins. It runs after `import openai` has had its say, so
an `OPENAI_LOG=debug` in the environment is undone. A DEBUG run of the real
client over a mock transport captures no sentinel from the prompt, the patient
text, the generated reply, the key or OpenAI's error message.

An autouse fixture makes `httpx2.AsyncHTTPTransport.handle_async_request`
raise, so a test that forgot the fake fails loudly instead of billing whichever
key is in the developer's environment.
