# VS-004: Worker + send a reply
Status: PARTIAL
Code complete and fully tested against a mocked Meta API (Tasks 1-9 of
`docs/plans/VS-004-plan.md`). Task 10, the live test with a real phone, has not
run: Meta still does not POST real messages to our callback URL, inherited from
VS-003's outstanding live verification. See that task for the two most likely
causes.

## Goal
Webhook enqueues a job; the worker processes it and sends a fixed reply through Meta.

## Scope
- Enqueue interface + arq implementation; webhook enqueues after storing
- Job: parse event -> resolve tenant (config mapping for now) -> upsert contact/conversation -> store message
- Meta client: send text message (timeout, retries on 5xx/429, no retry on 4xx)
- Reply "Received ✅" (temporary); store outgoing message; handle status events (sent/delivered/read)
- Failed after N attempts -> dead_letter_jobs

## Acceptance
- "Hello" from my phone -> "Received ✅" back on WhatsApp
- Webhook responds fast even if Meta send is slow (test with mocked delay)
- Tests with mocked Meta API: retry behavior, dedup still holds

## Understand first
Why the webhook must not wait for slow work; at-least-once delivery.

## Notes

- **A message job has three commits, and the order is the correctness.** T0 claims
  the inbox row and commits on its own; T1 stores the patient, the thread, the
  inbound message and a reserved reply row, and commits; then one Meta call; then
  T2 writes the returned `wamid` and marks the event `PROCESSED`.
- **The reply row is committed BEFORE the send.** Written in the same transaction
  as the wamid, a crash during the send would leave no trace that a send was ever
  attempted, and the retry would have nothing to recognise. Committed first, it is
  a durable "a reply to this message is in flight", and it is what the unique
  constraint uses to stop a second job starting a second reply.
- **The inbox row is marked `PROCESSED` only in T2.** Mark it earlier and a crash
  during the send makes the retry skip the send entirely — a patient message
  silently unanswered. The row therefore stays `PROCESSING` across the Meta call
  on purpose, which is why `claim()`'s guard is `status <> 'PROCESSED'` and not
  `status = 'RECEIVED'`.
- **The claim commits on its own (amendment A1).** Folded into T1, it is rolled
  back by every retryable error, which undoes `attempts + 1` — so a job that
  failed five times would report one attempt in its dead letter — and holds a
  write lock on the row for all of T1, so a concurrent worker *blocks* instead of
  being told `locked` at once. A lease only works if other transactions can see
  it, and in PostgreSQL that means committed.
- **`status` alone cannot serialise two concurrent runs, so there is a lease.**
  `PROCESSING` has to stay claimable for a try that died mid-send, so it cannot
  also mean "a live try owns this". Only time separates the two, which is what
  `webhook_inbox.locked_until` holds. Without it, two runs both claim the row,
  both find the same reserved reply row with no wamid, and **both send** — the
  reply row's unique constraint does not help, because it prevents two reply
  *rows*, not two sends from one row.
  - The lease is `JOB_TIMEOUT_SECONDS + JOB_LEASE_MARGIN_SECONDS` and must outlive
    the job: expiring mid-send is the duplicate it exists to prevent. `Settings.
    claim_lease_seconds` derives itself so the two knobs cannot be set into
    conflict, and a test asserts the ordering.
  - It is PostgreSQL's clock, evaluated server-side inside the claiming `UPDATE`,
    so a worker with a skewed clock cannot grant itself longer.
  - It is released on every exit **except** `locked`, which belongs to another
    worker. Holding it through a deferral would make the retry find its own stale
    lease, report `locked` against itself and defer again — one backoff curve
    turned into `max_tries` lease timeouts.
  - A worker killed with `SIGKILL` strands its event for the remainder of the
    lease. A bounded delay, in exchange for a duplicate that cannot happen.
- **Four idempotency keys, and not one of them is a check the code performs:**
  `webhook_inbox.provider_event_id` (Meta's duplicate), the arq job id (a double
  enqueue), `webhook_inbox.status` + `locked_until` (a re-run, and a simultaneous
  run — different problems), and `uq_messages_reply_to_message_id` (a second reply
  row). A check-then-act has a window; a constraint does not.
- **The arq job id is a short-lived key.** `enqueue_job` returns `None` for an id
  it already holds, but results expire (an hour by default) and the same id then
  runs again. That is why the worker also checks `webhook_inbox.status`: arq
  handles the burst, the database handles forever.
- **The one gap left: a duplicate reply.** If the process dies after Meta accepted
  the send and before T2 commits, the retry finds a reply row with no wamid,
  cannot tell the send succeeded, and sends again. It cannot be closed here —
  Meta's send endpoint has **no idempotency key**, and a timeout is genuinely
  ambiguous. The alternative ordering (mark `SENT` before calling Meta) makes a
  duplicate impossible and silent loss ordinary, which is worse. One extra
  `Received ✅` is visible and self-explaining; a missing reply is invisible.
  `sent_without_id` is the same gap from the other side: a 2xx we cannot read a
  wamid from is treated as success, because retrying would guarantee the duplicate.
- **A wamid is patient content.** It is base64 and commonly decodes to include the
  patient's phone number, and a status event id carries the wamid of the message
  *we sent to the patient*. So the job carries our `webhook_inbox` row UUID, not
  `provider_event_id`; `event_id=` in every VS-004 log line is that row id; the
  arq job id is `inbox:<uuid>`; and the dead letter references the row id too.
  VS-003 reasoned the opposite ("an opaque Meta identifier") — see the follow-up.
- **The webhook enqueues redelivered events too.** "Already stored, so already
  handled" loses the message whenever the *first* enqueue is what failed, which is
  one of the reasons Meta redelivers. The duplicate path looks the existing row id
  up rather than inventing one, which is what keeps arq's dedup and the lease
  working across redeliveries.
- **An enqueue failure answers 503, not 200.** The rows are committed and nothing
  would ever process them; 200 tells Meta to forget the event. Same reasoning as
  VS-003's storage-failure 503, one layer further in.
- **Classification lives in the Meta client; retries live in the job.** The client
  makes exactly one attempt and returns `SUCCESS | RETRYABLE | PERMANENT`. A retry
  loop inside it would make the backoff curve, `max_tries` and the dead letter all
  lie: five internal attempts inside five job tries is twenty-five sends, and
  `attempts` would say 5. `classify_exception` returns `None` for anything that is
  not an httpx transport error, so a bug in our own code raises instead of being
  retried five times and dead-lettered as an outage.
- **arq does not retry a plain exception.** Only `Retry` (and cancellation, under
  `retry_jobs`). The envelope raises `Retry(defer=backoff(job_try))` itself, which
  is also what gives us a curve we control: 5s, 10s, 20s, 40s, then a dead letter.
- **`error_reason` is built from Meta's numeric codes only** and never reads
  `error.message`, `error.title` or `error.error_user_msg` — those quote the
  recipient's number for the single most common test-number failure. It is
  deliberately **not** passed through `scrub`: `error_subcode` values are seven
  digits (`2494010` is "recipient not in the allowed list"), so the digit-run
  redaction would eat the most useful code in the string. `scrub` is for
  Meta-supplied *strings*, and `error_reason` exists to make sure none reaches it.
- **Status ranks: `QUEUED`/`RECEIVED` 0, `SENT` 1, `FAILED` 2, `DELIVERED` 3,
  `READ` 4**, compared with `>` inside the `UPDATE`'s `WHERE` clause so two
  callbacks cannot interleave a read and a write. `FAILED` sits above `SENT` and
  below `DELIVERED` on purpose: a send Meta later reports as failed must overwrite
  `SENT`, and a message that was delivered did not fail.
- **The status handler looks the message up before advancing it**, and the lookup
  is not redundant with `advance_status`'s boolean. "No such wamid" is Meta's
  ordinary out-of-order delivery and is retryable; "found but did not move" is an
  old or repeated callback and is a success. One boolean cannot tell them apart,
  and conflating them either loses a real status or dead-letters a duplicate.
- **A status word we do not model is ignored, not dead-lettered.** Meta adds values
  (`deleted`, `warning`) without notice, and one dead letter per unrecognised word
  would fill a triage table with things nobody will ever act on.
- **`dead_letter_jobs.payload` is a reference, not the event** —
  `{inbox_row_id, kind, phone_number_id, job_try}`. VS-002's docstring said it
  would hold the same patient content as `webhook_inbox.payload`; a table people
  open casually to triage failures must not be a second copy of a patient's
  message under a second retention policy. `source_event_id` points at the row
  that has the whole thing.
- **`MessageModality.OTHER` was added by a hand-written CHECK-swap migration.**
  "Store all inbound message types" is impossible for an image or a location
  without it, and `app/db/enums.py` prescribes exactly this route — VARCHAR +
  CHECK precisely so widening is reversible, which `ALTER TYPE ... ADD VALUE` is
  not. `audio` maps to `VOICE_NOTE` here rather than in VS-008, so a voice note
  stored today is already the right shape for a transcript.
- **Two savepoints, because a failed INSERT aborts the whole transaction in
  PostgreSQL** (amendment A2). `MessageRepository.add` and
  `ConversationRepository.get_or_create_open` wrap their flush in
  `session.begin_nested()`. Without it, the job's `except DuplicateRecordError:
  re-read the existing row` — which is what makes a re-run safe — would raise
  `InFailedSqlTransaction` on that very re-read. `reserve_reply` and the contact
  upsert need nothing: `ON CONFLICT DO NOTHING` cannot fail.
- **Hard rule 7 is applied even though this reply is not from an AI**, and the
  state is re-read from the database immediately before the send rather than
  trusted from the get-or-create earlier in the job. `HUMAN_REQUESTED` still gets
  a reply: going silent between "the patient asked for a human" and "a human
  picked it up" is the worst of both. A `CLOSED` conversation is not a drop — it
  frees the partial unique index, so a new `AI_ACTIVE` thread opens and is
  answered, which is the documented state machine.
- **`.env.example` keys with empty values are a real trap.** `META_API_VERSION=`
  sets the variable to `""`, which pydantic accepts as a perfectly good `str`, and
  the send URL would lose a path segment. A `mode="before"` validator treats a
  blank value as unset for `meta_api_version` and `meta_api_base_url` only —
  never for a credential, where "not configured" must keep meaning "every request
  fails visibly". The tenant map and the reply-type filter are `str` fields for
  the same family of reasons: a typed `dict`/`list` would be JSON-decoded and a
  blank value would stop the app booting from its own example file.
- **`tests/api/conftest.py` has an autouse `queue` fixture.** From this slice on
  the webhook enqueues on every successful POST, and without the override every
  endpoint test would open a real Redis pool — passing on a machine with Redis up
  and failing everywhere else.
- **`tests/worker/conftest.py` uses sessions that really commit**, not the
  rollback-wrapped `db_session`: the job commits three times and reads its own
  writes back across transactions. An autouse fixture truncates afterwards, and
  only for tests that asked for a database.

## Follow-ups

- ~~**VS-003's webhook still logs wamids.**~~ **RESOLVED in review.** Its
  happy-path line printed `provider_event_id` values, on the premise that a wamid
  is "an opaque Meta identifier, not patient content". That premise is wrong (see
  the Notes), and this was the one line in the system that printed one on every
  successful delivery — so it now logs `webhook_inbox` row ids like everything
  else. `tests/api/test_webhook_logging.py` asserts the row ids are present and
  the wamids are absent, where it used to assert the opposite, and the
  end-to-end wamid sweep no longer excludes any line.
- **The duplicate-reply gap.** Two things would narrow it: reading back Meta's
  message list for the conversation before resending, and a short-lived
  "send in flight" marker with its own timestamp so a retry can wait out Meta's
  processing window rather than sending immediately.
- **A worker killed with `SIGKILL` strands its event for the rest of the lease.**
  Acceptable, and bounded; if it turns out to matter, a heartbeat that extends the
  lease while a job is alive is the usual answer.
- **No jitter on the backoff.** These jobs are keyed per message and do not
  stampede, but Meta's per-number rate limit could make many fail on the same
  tick. Add jitter if a 429 storm ever shows up.
- **A status for a wamid we never sent retries five times and then dead-letters.**
  A message sent by hand from the Meta Business app produces exactly this. Fixing
  it needs a record of wamids we have sent, which we do not have; until then the
  dead letter says `status_before_wamid` and is harmless noise.
- **No error column on `messages` for a `failed` callback.** Meta's codes are
  logged and then gone. A `last_error` on the row would make "why did this reply
  fail?" answerable from the table the reply is in.
- **`WHATSAPP_TENANT_MAP` has no validating helper.** A typo is invisible until the
  first event dead-letters. A `scripts/` command that parses it and prints the
  entry count would catch it at deploy time.
- **Still no index on `webhook_inbox.status`** (VS-002's follow-up), deliberately:
  the worker's only lookups are by `id` and `provider_event_id`, both already
  unique-indexed. It is an ops-query index, and no ops query is written yet.
- **Retention now covers `messages.text` as well as `webhook_inbox.payload`.** The
  conversation itself is patient content and cannot be avoided; pair the policy
  with VS-008's audio retention.
- **Structured logging with a correlation id** is more valuable than ever: one
  message is now a webhook line, an enqueue, up to five job tries and possibly a
  dead letter. Every VS-004 line carries `event_id=` as a poor substitute.
- **`HUMAN_REQUESTED` still gets an AI reply.** Decided for VS-004: hard rule 7
  names only `HUMAN_ACTIVE` and `CLOSED` as the drop cases, and going silent
  between "the patient asked for a human" and "a human picked it up" is the worst
  of both. **To be revisited in VS-010**, which owns the handoff workflow and is
  the slice that can say what should happen in that gap.
- **A last try that ends in `event_locked` writes a spurious dead letter.** The
  envelope's retryable path dead-letters on the final try whatever the reason, and
  `_dead_letter` marks the inbox row `FAILED` — while another worker still holds
  the lease and is very likely about to finish the work successfully. The row then
  says `FAILED` for an event that was in fact handled. Rare (it needs five
  consecutive collisions on one event), harmless to the patient, and misleading in
  triage. Fix later: `event_locked` should defer without consuming a try, or at
  least not dead-letter.
- **A worker killed on arq's final try leaves a row nothing will ever retry.**
  When `job_try` has reached `max_tries`, arq gives up without calling the job
  again — so if the process dies on that last try, our code never runs, no dead
  letter is written, and the row stays `PROCESSING` with an expiring lease and
  nothing left to claim it. It is invisible: no reply, no dead letter, no error.
  Needs a sweeper — a cron job over `webhook_inbox` rows that are `PROCESSING`
  with an expired lease and older than some threshold, re-enqueueing or
  dead-lettering them. **The most important item on this list.**
- **`ACK_TEXT` is a constant in `app/worker/jobs/inbox.py`** and VS-005 deletes it.
  It is not a setting on purpose — a knob nobody will turn, on a value that is
  about to disappear.
